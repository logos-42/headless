# 阶段三:单因素生存边界扫描

**日期**: 2026-09-27
**目标(leo 的定义)**:**不是找"最优参数",是画出机制边界** ——
安全区间 / 危险区间 / 默认值落在哪里。
**方法**: 每次只动一个参数,其余全部用 `docs/calib_baseline_freeze.md` 的冻结契约;
三场景(normal / inert / harm)各 300 回合; 按 leo 的六类失效归类。
**代码**: `tests/sweep_rr_survival.py`; 原始数据 `results/sweep_stage3.json`。

## 一、总表

## 二、逐条:边界长什么样,为什么

### rr_forgive_p —— 唯一一个**双侧**窗口,也是最干净的一个

    0.0   normal 末段 未/好/坏 = 0/0/2 ... **0 个"好", 2 个"坏"**
          同时命中: 正常 option 被判坏 / 主任务恶化(inert 与 harm 输出逐位相同)
    0.02  ✔ detect 4, 故障段成功 0.983
    0.10  ✔ detect 33, 成功 0.567     <- 默认
    0.3   ✘ 未能自救 / 过度激进(判坏后仍在用)

**`rr_forgive_p = 0.0` 是有力的负对照**: 连**无故障**的 normal 场景都以
「0 好 / 2 坏」结束 —— 一旦某个 option 被误判为坏,它就再也不被使用,
统计量冻结,于是永远坏。**退休不可逆 = 判据无法自救**,在正常场景里就能复现。

**但默认值可能偏保守**: `0.02` 在 harm 上 `detect 4 / 成功 0.983`,
明显优于默认 `0.10` 的 `detect 33 / 成功 0.567`。这条**只有 1 seed**,列进阶段三待确认项。

### rr_forget_hl —— 唯一的**单调**剂量响应

    inf   detect 406  ✘ 检测过慢
    200   detect 138
    50    detect 77
    20    detect 33   <- 默认

半衰期越短、检测越快,**完全单调**。`inf`(终身统计)是最差的一档:
旧账把故障前的"健康"记了一辈子,于是系统看不见故障。
这与之前"持久化必须配遗忘"的结论一致,这次给出了完整的剂量曲线。

### rr_starve_steps —— leo 点名要确认的那一条

    (步)   倍数        inert 故障段               fallback
    5      0.17×   ✘ 误杀 1、检测延迟 779        0.584
    15     0.5×    ✔                            0.318
    30     1×      ✔                            0.318
    90     3×(默认) ✔                            0.167
    300    10×     ✔                            0.000
    1000   33×     ✔                            0.000

**答案: 它不是 horizon 调出来的刀口。** 安全区间从 **0.5× 一直延伸到 33× horizon**,
默认 `3×` 居中枢而**不是边界值**。

为什么低端危险: 训练中"暂时没拿到奖励"是**正常现象**(还在探索、还没走到终点)。
阈值压到 0.17× horizon 时,这种正常间隔被读成"全局奖励流为空",
于是把整段统计判成未知/触发退回基元 —— **inert 误杀**(检测延迟 779)。

**因此可迁移的说法是**: `rr_starve_steps` 的下界由「**两次奖励之间的正常间隔**」
决定,不由 horizon 决定。在 KeyDoor 上这个间隔 ≤ 15 步,所以 0.5× horizon 就够了。
换环境时应当按"最长正常无奖励间隔"取值,而不是照抄 `3×horizon`。
(诚实边界: 目前只有 KeyDoor 一个环境,这条**推理**尚未在第二个环境上验证。)

### rr_lr_v —— 低端坏在"判据没有分辨力",不是"学得慢"

    0.05  ✘ harm 末段 未/好/坏 = 2/0/0, 成功 0.450 「未能自救」
    0.2   ✔ 默认
    0.5   ✔ 成功 0.683, 但 detect 115(更慢)

`0.05` 的失效形态值得注意: 它**不是**"什么都不做",而是**检测很快(10)却救不回来**。
Φ 太慢 -> `advq` 基本是噪声 -> 判据在噪声上开火 -> 提前退休;
同时 Φ 又不足以把"好 option 回来了"这件事学出来 -> 恢复不了。
**传感器噪声与检测器灵敏度是一回事** —— 判据的可靠性受限于势函数的学习速度。

诚实存疑: 检测延迟随 `lr_v` **非单调**(10 -> 33 -> 115),
和"学得快应当判得准"的直觉相反。1 seed,未归因,列入待确认。

### rr_unk_p / rr_min_launches —— 激进端触发误杀

    rr_unk_p = 1.0      ✘ 误杀健康 option ×1(总是优先探索未知)
    rr_min_launches=12  ✘ 误杀健康 option ×1

两者的失效方向一致: **"未知"的处理一旦太激进,就会把健康的 option 卷进去**。
`rr_unk_p=1.0` 意味着只要有未知 option 就优先挑它 —— 反复重测让噪声有机会处决一个好的。
`min_launches=12` 让 option 长期停在未知,于是持续被"优先探索"挑中,同一个后果。

**这两条直接支持三态设计里"有限度探索"而不是"无限探索"的选择** ——
`rr_unk_p=0.5` 是安全的,`1.0` 不是。不过 0.0 也安全且 detect 更快(9 vs 33),
所以"要不要探索未知"在**这个测试台**上没有明显收益; 保留 0.5 是为了机制完整性
(未知若永远不被选,就永远无法变成好/坏),而不是因为量到了收益。

### rr_ucb_c —— 唯一没有危险区的参数

0.5 / 1.0 / 2.0 全部安全(检测延迟 24 / 33 / 103)。
在这个测试台上 UCB 系数**不构成生存风险** —— 这也说明**它目前不是一个敏感旋钮**,
列进"可以保持默认、不必再扫"的一类。

## 三、分类器本身修了两处(都记在提交里)

1. **归类必须按场景** —— 第一版把 `detected is False` 无条件当成
   "坏 option 长期存活",于是 normal / inert(本来就没有 harm 故障)全被误标。
   场景不同,"失效"的定义也不同。
2. **fallback 的分母错了** —— 原用 `starved_sel / selections`,
   但 `selections` 只在真的选中时 +1,比值可以 > 1(实测 **6.827**)。
   改为 `starved_sel / sel_attempts`(选择**尝试**总数)。

这两处都是"判据自己错"在下结论前被抓到 —— 属于同一类,值得记进方法论:
**报告出来一个不可能的数值(>1、逐位相同、恒零)时,先怀疑算它的人。**

## 五、待确认(1 seed 项,需要 3 seeds × 300 回合)

1. `rr_forgive_p = 0.02` 是否真的优于默认 `0.10`(harm 成功 0.983 vs 0.567);
2. `rr_lr_v` 的检测延迟**非单调**是否稳定;
3. `rr_min_launches = 12` 的误杀是否为稳定效应;
4. `rr_starve_steps` 的"下界 = 最长正常无奖励间隔"需要在**第二个环境**上验证 ——
   这是唯一一条跨环境可迁移性尚未验证的推理。
