## 二、三个"结论"全部被推翻,真凶唯一

| 曾得出的结论 | 现状 |
|:--|:--|
| "OML 不适合持续学习" | ❌ **错**。OML2+PLN = 0.7401,是全场最优 |
| "PLN 头是元凶" | ❌ **错**。PLN 0.7287 vs 线性 0.7368,无差异 |
| "天花板 vs 保留率是架构权衡" | ❌ **错**。也是同一个 bug |

**三者都是 BatchNorm 统计量随域漂移这一个 bug 造成的假象。**

BN 的 running stats 在持续学习中被当前域更新,旧域数据被错误统计量归一化
→ 特征整体扭曲 → 表现为"方法不行/头不行/架构有本质权衡"。

### 方法学教训(值得写进论文的附录)

1. **一个实现 bug 可以伪装成三个"科学结论"。** BN 漂移同时污染了
   方法对比、头对比、架构对比 —— 因为它在所有配置里都生效。
2. **反直觉的好结果必须当 bug 追。** 本轮三次:naive 跨年 1.000、
   BN 漂移、跨年指标设计错误。**反直觉 + 数字太漂亮 = 先怀疑实现。**
3. **排除一个假说后必须继续找真因。** 容量扫描时发现"连 h32 都只有 0.27",
   判断"不是容量"是对的,但停在那里就错了 —— 真因是 BN。
4. **一次只变一个变量。** 早期同时改 backbone 默认值和 head,
   导致 si_d3 与 si_d6/si_d12 配置不一致,数字不能横向比。

## 四、设计约束

`--cl-method oml/oml2` **需要可适应头**(PLN 或 SwiftTD):
它们是元学习过程, 要用 `clone_params` / `step_beta` 做内循环适应,
普通 `nn.Linear` 头没有可适应参数。main() 已加守卫: 自动切 pln 并警告。
